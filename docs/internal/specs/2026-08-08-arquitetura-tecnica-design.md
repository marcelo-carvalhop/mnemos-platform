## 1. Scope

The functional spec covers screens, flows and business rules, and states explicitly that it does not cover backend architecture or the device. This document is that missing layer, for **all of v1** — including subsystems (generation, quota, billing) that have no screens drawn yet, because the schema must support them regardless.

Out of scope, unchanged from §7 of the functional spec: the e-reader device, marketplace and social features, and the explicitly discarded list (Anki/CSV import, cloze, images on cards, browser extension, etc.).

## 3. The organising principle

§3 of the functional spec says a review is an immutable event and that *all scheduling and all statistics derive from that history*. That is not only a business rule — it is the architecture, and four properties fall out of it:

1. **Scheduling state never needs to sync.** The history does; each device recomputes from it.
2. **History cannot conflict.** Append-only logs merge by union, so the highest-volume and most irreplaceable data needs zero conflict-resolution code.
3. **"Editar um card não altera seu agendamento" (§3) is structural.** Content and schedule live in different tables; breaking it would require deliberate effort.
4. **"Reiniciar progresso" (§5.10) is non-destructive.** It writes a marker that replay respects, so the schedule resets while the history survives.

Consequently `card_state` — stability, difficulty, due date — is a **rebuildable cache**, never a source of truth.

### 3.1 What the principle actually requires

"Each device recomputes and gets the same answer" is only true if every input to the computation is the same on every device. Three inputs are not the review log, and all three are easy to forget:

| Input | Where it must live |
|---|---|
| The review history and its reset markers | synced, two-way, as a union (§6.1) |
| The FSRS parameter vector and `desired_retention` | synced settings (§5.4) — `desired_retention` is a term in the interval formula |
| Randomness | there must be none — interval fuzz is disabled (§4.1) |

Miss any of the three and two devices produce different `due_at` from identical histories, which falsifies the whole premise. These are stated here rather than buried in the data model because they are the load-bearing constraint, not an implementation detail.

## 4. Topology

```
flashcards/
├─ shared/
│  └─ contract.yaml           single source of char limits, enums, error codes
├─ app/                       Flutter client — not containerised (§11.7)
│  ├─ packages/
│  │  ├─ scheduler/           pure Dart · FSRS · zero I/O · no randomness
│  │  └─ domain/              entities + value types, no deps
│  └─ lib/
│     ├─ store/               drift (SQLite) · tables, DAOs, FTS5
│     ├─ sync/                outbox push + delta pull
│     ├─ api/                 generated client (server OpenAPI)
│     └─ features/            one module per screen group
├─ server/                    FastAPI
│  ├─ auth/  sync/  quota/  billing/
│  ├─ generation/             LLM jobs, prompts
│  ├─ ingest/                 upload, page-range slicing, size/format validation
│  ├─ worker/                 Postgres-backed queue consumer
│  └─ migrations/             alembic — run as a job, never at container start
├─ docker/
│  ├─ server.Dockerfile       multi-stage; one image, two commands
│  └─ entrypoint.sh
├─ compose.yaml               postgres · minio · server · worker
├─ .dockerignore
└─ .env.example               names of every variable, values of none
```

Dependency direction is strictly `features → sync → store → domain`, with `scheduler` hanging off `domain` alone.

`shared/contract.yaml` generates a Dart file and a Python module. Character limits, the `grade` and `source` enums, and the machine-readable error codes are declared once and consumed by both sides. A constant duplicated across two languages diverges; §7.6 depends on it not diverging.

### 4.1 The `scheduler` package

A pure Dart package: no Flutter, no database, no ambient clock — time is injected. Its entire public interface:

```dart
/// The single place a grade becomes a new state. Everything else derives from it.
CardState apply(CardState state, Grade grade, DateTime at, FsrsParams params);

CardState replay(List<Review> history, List<ProgressReset> resets, FsrsParams params);

Map<Grade, Duration> preview(CardState state, DateTime now, FsrsParams params) =>
    {for (final g in Grade.values) g: apply(state, g, now, params).dueAt.difference(now)};
```

Three things about this signature are deliberate:

- **`preview` is derived from `apply`, not parallel to it.** §5.8.3 requires each of the four grade buttons to display its resulting interval *before* the user commits. Deriving the preview from the same function that writes the state makes "the preview never lies" true by construction rather than by test.
- **`preview` takes `now`.** The resulting interval depends on retrievability at review time, which depends on how long the card has been due. A card overdue by three days does not produce the same four intervals as one reviewed on schedule. Omitting this parameter is the quiet way to ship a preview that is wrong for exactly the cards the user cares about.
- **Everything takes `params`.** See §3.1.

**No randomness.** FSRS ports commonly apply a random "fuzz" to intervals of about 2.5 days and up, to spread load. The wrapper disables it explicitly and a test asserts it stays disabled. Fuzz would break the property test in §12 (*replaying a log twice yields identical state*) intermittently, and — worse — would make two devices compute different due dates from the same history, which is the failure the entire design is built to prevent.

Isolating this way means the correctness-critical logic is testable with plain data. Scheduling bugs surface *weeks* later as "why is this card due today", so being able to assert against thousands of synthetic histories in milliseconds is worth the package boundary.

**Implementation:** wrap the existing `dart-fsrs` port behind our own `Scheduler` interface. The wrapper provides `preview`, pins the fuzz setting, and keeps the dependency swappable.

### 4.2 Server modules

`generation` and `ingest` are off the request path entirely: an endpoint enqueues, a worker executes. FastAPI's `BackgroundTasks` is insufficient — multi-second model calls need a real queue with progress reporting and retry.

**The queue is Postgres, not Redis.** `generation_jobs` already lives in Postgres and the worker claims rows with `SELECT ... FOR UPDATE SKIP LOCKED`. Three reasons this beats `arq`/Redis here:

1. **Quota reservation and enqueue must be atomic.** §7.7 reserves quota when the job is created. With quota in Postgres and the queue in Redis that is a distributed commit, and its failure mode is charging a user for a job that never ran. In one database it is one transaction.
2. **No duplicated job state.** A Redis queue plus a `generation_jobs` table is the same fact in two places that can disagree.
3. **Durability.** Redis-as-queue is at-least-once and loses work on restart without persistence configured. For a job that spends metered money, that is the wrong default.

At this product's volume, a table-backed queue is not a compromise — it is fewer moving parts, and it matches the deliberate decision that one service owns everything. Revisit if job throughput ever justifies dedicated queue infrastructure.

**Each module is `router → service → repository`.** FastAPI itself — request and response models, dependency injection, status codes — stays in the router; the service holds the business rules and imports nothing from `fastapi`; the repository owns SQL. The rule earns its keep in one specific place: §7 is the same logic reached from an HTTP request and from a worker with no request at all, and a service that takes a `Request` cannot be called by the worker. It also makes the quota and sync rules testable without starting the app.

### 4.3 The API contract and its documentation

FastAPI generates OpenAPI from the route signatures, so the contract is a build artefact rather than a document someone maintains. Sub-project 0 (§14) depends on it: the generated Dart client is committed, and a contract test fails when the schema drifts from it.

Two things this requires in practice. **Every route declares an explicit `operation_id`** — without it the generated Dart method names are derived from paths and are unreadable. And **response models are declared, not inferred**, or the generated client types half the API as `dynamic`.

Swagger UI is served at `/docs` in development and **disabled in production**. The API is private to one app; the interactive documentation leaks no data but publishes the full surface to anyone probing. Turning it off costs nothing, because the OpenAPI JSON that matters is generated at build time for codegen, not scraped from a running server.

### 4.4 Client composition and state

**Riverpod.** The decisive property is that providers are testable without a widget tree, which is what makes §12's "light on widget tests" honest rather than a gap: session logic, queue construction and sync state are exercised as plain Dart. It also injects the clock and the repositories — `scheduler` takes time as a parameter (§4.1) and something has to supply it — and consumes `drift`'s query streams directly, so the UI reacts to local writes without a manual refresh, which is the normal case in an offline-first app.

Layering follows the dependency direction: a `features` module reads providers and renders; providers hold no SQL and no scheduling arithmetic. `scheduler` and `domain` are separate packages precisely so the direction is enforced by the build rather than by discipline (§12).

## 5. Data model

Three tiers, distinguished by how they sync.

### 5.1 Tier 1 — Content (mutable, two-way LWW)

```sql
decks(id PK, parent_id, name, description, version,
      author, license, origin, source_deck_id, archived_at,
      updated_at, deleted_at, device_id, server_seq)

cards(id PK, deck_id, front, back, tags,
      updated_at, deleted_at, device_id, server_seq)

card_flags(card_id PK, status, buried_until,
           updated_at, device_id, server_seq)
```

**`tags` is a value of the card**, not a join table — `text[]` in Postgres, JSON in SQLite. A `card_tags(card_id, tag)` join table has no place to put a tombstone, so removing a tag offline and syncing makes the tag reappear. As a column, the card row is the unit of LWW, which matches how the UI edits tags anyway (§5.4 and §5.7 of the functional spec always edit tags together with the card). A local `card_tags` index table, maintained by trigger, still serves the tag filter of §5.10 without participating in sync.

**`card_flags` is separate from `cards` for a reason.** Row-level LWW loses concurrent edits to different fields of the same row: burying a card on the phone while fixing a typo on the tablet would discard one of the two. Worse, `buried_until` is state that expires in 24 hours — syncing it inside the content row means a trivial daily write competes with real text edits. Splitting the volatile state into its own row with its own clock makes both operations survive.

`status` ∈ `active | suspended | buried`. `version`, `author`, `license`, `origin`, `source_deck_id` carry no UI in v1 — they exist because §7 requires shared decks not to force a migration later. **`version` is reserved and unused in v1**; it gets semantics when shared decks do. The risk with these fields was never the schema migration (a nullable column is trivial in both databases) — it is accumulating divergent implicit meaning between client and server, so the unused one is labelled unused.

`decks.parent_id` allows nesting. Three rules the implementation must enforce, because a tree without them corrupts quietly: writes reject cycles (on both client and server), depth is capped, and deleting a deck soft-deletes its subtree. An archived deck (`archived_at`) is excluded from study sessions but keeps its cards and their history.

### 5.2 Tier 2 — History (append-only, two-way union)

```sql
reviews(id PK, card_id, reviewed_at, grade, source,
        elapsed_ms, device_id, server_seq,
        interval_days_after, stability_after, difficulty_after,
        scheduler_version, app_version)

progress_resets(id PK, card_id, reset_at, device_id, server_seq)

goal_history(id PK, effective_from_local_date, daily_goal,
             created_at, device_id, server_seq)
```

`goal_history` is here — in the append-only tier rather than in settings — because the streak needs the goal that was in force on a past day, and a setting only ever holds the current value. §9 explains why that distinction is what keeps the streak from rewriting itself. The goal in force on any date is the row with the greatest `(effective_from_local_date, created_at, id)` at or before it; the triple makes the answer identical on every device even when two of them change the goal on the same day.

`reviews` accepts no `UPDATE` and no `DELETE`. This is enforced two ways, because §3's guarantee is only as strong as its weakest caller:

```sql
REVOKE UPDATE, DELETE ON reviews FROM app_role;   -- the application simply cannot
CREATE TRIGGER reviews_immutable BEFORE UPDATE OR DELETE ON reviews
  FOR EACH ROW EXECUTE FUNCTION raise_immutable();  -- explicit error if anything else tries
```

Privilege revocation is stronger and cheaper than a trigger; the trigger exists so that a mistake made through a privileged role fails loudly instead of succeeding. SQLite gets the equivalent trigger. Account deletion (§8.4) is the one sanctioned path around this, and it runs as a separate administrative role.

That constraint is what makes `progress_resets` necessary: §5.10's *reiniciar progresso* cannot delete history without breaking immutability, so it writes a marker and replay ignores everything before it. The user gets a card that starts from zero; statistics still see the whole truth.

`grade` is a `smallint`, 1–4, mapped in `shared/contract.yaml` (1 = errei … 4 = fácil). Never a string, never renumbered.

`source` ∈ `standard | multiple_choice`. §5.9 says multiple choice counts for FSRS but the leech drill, timed simulado and TTS explicitly do not — so **those modes write no review row at all**. The question "does this feed the scheduler?" is therefore answered by whether a row exists, not by a flag someone has to remember to check.

**Multiple choice needs a documented grade mapping**, because it is a scheduling decision and not a UI one. Four options means roughly a 25% chance of a correct guess; mapping "correct" onto *bom* or *fácil* inflates stability with noisy signal and degrades the user's schedule over months. The conservative mapping: wrong → *errei*, correct-and-slow → *difícil*, correct-and-fast → *bom*. **`fácil` is never inferred.**

**The trailing columns are written once, at insert, and are advisory.** `interval_days_after` makes the graduation milestones of §5.11 a query instead of a replay; the stability and difficulty snapshots make retention-over-time charts possible without recomputation; `scheduler_version` and `app_version` make it possible to tell, after an algorithm change, what the app actually did at the time. None of this violates §3 — nothing is ever updated. But they are **not authoritative**: a review written on device A under different parameters can disagree with device B's replay. `card_state` always comes from replay, never from these columns.

### 5.3 Tier 3 — Derived (never synced, rebuildable)

```sql
card_state(card_id PK, stability, difficulty, due_at,
           last_review_at, reps, lapses, phase,
           computed_through_reviewed_at, computed_through_review_id,
           fsrs_params_version, dirty)
```

The watermark is a `(reviewed_at, id)` pair rather than a single review id, because with two-way history sync a review can arrive **out of order** — device B records a review at 09:00 and it reaches device A after A has already advanced past 10:00. Incremental replay would silently skip it.

The rule: any insert whose `reviewed_at` falls below the watermark sets `dirty`, and a background pass fully replays those cards. Replaying one card is cheap; replaying the account is not, which is why the flag is per card. Normal operation still appends one review and advances one step; full rebuild is the fallback, not the hot path.

`fsrs_params_version` triggers the same rebuild when the parameter vector or the algorithm version changes. Without it, an app update that changes FSRS would leave every card scheduled by a mix of two algorithms with no way to tell which.

**Maturity is deliberately not a column.** §4 says "maduro" is not a real state, only a cut of "em revisão", so it stays a query predicate (`interval > 21d`). Same for deck progress — computed, never stored.

### 5.4 Settings — synced and local

Settings split by whether they affect the schedule. Anything that is an input to FSRS must be the same on every device (§3.1); anything else stays where it is set.

```sql
-- synced, two-way LWW, like any other entity
user_settings(key PK, value, updated_at, device_id, server_seq)
--   desired_retention, fsrs_params, fsrs_params_version,
--   new_per_day, timezone, day_cutoff_hour

-- never leaves the device
local_settings(key, value)     -- TTS voice, theme, notification time
sync_state(last_pulled_seq, device_id)
```

`desired_retention` is a term in the FSRS interval formula. Leaving it device-local — as the first draft did — means two devices compute different due dates from identical histories. It is not a preference; it is a scheduler input that happens to be exposed as a preference.

**`daily_goal` is deliberately absent from this table.** It lives in `goal_history` (§5.2), and the current goal is the most recent row. Keeping a copy here as well would be the same fact in two places that can disagree — the objection this document already raises against a Redis queue beside a jobs table (§4.2). The goal editor (`12 Meta diária`) reads the latest row and writes a new one.

The client-side mirrors of server-owned data are unchanged in spirit:

```sql
generation_jobs(...)     -- read-only mirror of the server's rows
pending_cards(...)       -- server-sourced mirror; `decision` is written locally
```

This is what lets the approval queue be triaged with no network — the cards were fetched when generation completed, and the decisions sync later.

### 5.5 Server (Postgres)

Mirrors tiers 1 and 2 with `user_id` on every row, plus `users`, `devices`, `refresh_tokens`, `quota_usage`, `subscriptions`, and the authoritative `generation_jobs` / `pending_cards` the client drains.

**Client-generated ids move identity assignment outside the trust boundary**, so the server enforces ownership rather than trusting the payload:

- `user_id` is always derived from the token, never read from the request body, and never mutable on an upsert.
- A pushed card's `deck_id` must belong to the pusher; a pushed review's `card_id` must belong to the pusher. Otherwise a client can write into another account by guessing — or simply reusing — an id.
- Row-Level Security is the structural version of this: a policy of `user_id = current_setting('app.user_id')::uuid` on every table makes cross-account writes impossible rather than dependent on a `WHERE` clause nobody forgets.

### 5.6 Indexes

The access patterns are narrow and known, so the index set is small and belongs in the schema from day one:

```sql
-- the hot path: today's queue
CREATE INDEX ON card_state(due_at) WHERE due_at IS NOT NULL AND NOT dirty;
-- replay
CREATE INDEX ON reviews(card_id, reviewed_at, id);
-- deck listing and counts
CREATE INDEX ON cards(deck_id) WHERE deleted_at IS NULL;
-- pull cursor (server)
CREATE INDEX ON cards(user_id, server_seq);
CREATE INDEX ON decks(user_id, server_seq);
CREATE INDEX ON reviews(user_id, server_seq);
-- heatmap and stats (server)
CREATE INDEX ON reviews(user_id, reviewed_at);
```

The queue query joins `card_flags` to exclude suspended and buried cards; that join is on the primary key and needs no extra index.

**Full-text search** (§5.10 requires search over cards) is SQLite FTS5, kept in sync with `cards` by trigger:

```sql
CREATE VIRTUAL TABLE cards_fts USING fts5(
  front, back, content='cards', content_rowid='rowid',
  tokenize="unicode61 remove_diacritics 2"
);
```

`remove_diacritics 2` is not optional in Portuguese: without it, searching "funcao" does not find "função" and the feature reads as broken.

### 5.7 Cross-cutting rules

**IDs are client-generated UUIDv7.** Offline creation cannot wait for a server to assign identity, and v7's time-ordering preserves index locality that random v4 would destroy. Ownership is verified server-side (§5.5).

**All timestamps are UTC milliseconds. Day boundaries are computed from a stored IANA `timezone` and a `day_cutoff_hour`, both synced settings.** Two decisions hide in that sentence:

- The timezone is stored and editable, not read from the device. Reading the device means the heatmap rewrites itself when the user flies to Lisbon.
- The day rolls over at **04:00 local by default**, not midnight. Studying at 01:00 otherwise counts as the next day, which breaks the streak of exactly the people who study late. This is the convention serious SRS apps use, and it costs nothing to adopt now.

One shared day-bucketing function serves the daily goal, "enterrado até amanhã" (§4), the heatmap and the streak (§5.11). Beware `AT TIME ZONE` around daylight-saving transitions.

**Every synced table carries `server_seq`.** See §6.2 — it is the pull cursor, and it is the server's to write.

## 6. Sync protocol

Asymmetric by design: the mechanism matches the value and volume of the data.

### 6.1 What syncs, and how

| Data | Direction | Merge |
|---|---|---|
| `reviews`, `progress_resets`, `goal_history` | two-way | **union** — insert on conflict do nothing |
| `decks`, `cards`, `card_flags`, `user_settings` | two-way | row-level LWW on `updated_at`, tie-broken by `device_id`, tombstoned by `deleted_at` |
| `generation_jobs`, `pending_cards` | server → client | server-owned; client pulls |
| `pending_cards.decision` | client → server | single-column push, idempotent (§7.8) |

**History is two-way, and that is not a contradiction of "append-only".** The first draft made reviews push-only, which meant a second device never learned what the first had studied: it recomputed `card_state` from a partial log, showed already-reviewed cards as due, and both devices drifted onto histories that never happened. Reinstalling the app had the same effect — the history sat on the server with nothing to bring it back.

Pulling reviews costs nothing in complexity, because the merge is a union: `INSERT ... ON CONFLICT (id) DO NOTHING` on both sides. Conflict is still impossible by construction. The second property in §3 is intact; only the word "push-only" was wrong.

LWW is genuinely lossy for concurrent edits. It is acceptable here because this is a single-user product whose only concurrency is one person on a phone and a tablet, and the worst realistic outcome is a card edit made offline on two devices where one wins and the user retypes a sentence. Splitting volatile state into `card_flags` (§5.1) removes the case where that loss is silent and surprising.

### 6.2 The cursor is `server_seq`, not a timestamp

Pull is a keyset delta over `(server_seq, id)`. `server_seq` is a per-user monotonic bigint assigned by the server inside the same transaction as the upsert.

The obvious alternative — filtering on `updated_at` — loses rows silently, in two ways:

- **Clock skew.** `updated_at` is written by the device, because it is the LWW criterion. A device whose clock is ten minutes slow writes rows *below* a watermark another device has already passed, and those rows are never pulled again. A fast clock is worse: the row wins every future LWW comparison, permanently.
- **Commit order.** Even with perfect clocks, a long transaction that starts at T1 and commits after one that started at T2 > T1 is invisible to anyone who has already pulled through T2.

Separating the two concerns fixes both:

| Field | Written by | Purpose |
|---|---|---|
| `updated_at` | client | LWW comparison, `device_id` tiebreak |
| `server_seq` | server | pull cursor, monotonic per user |

Keyset pagination over `(server_seq, id)` also removes the classic boundary bug where rows sharing a timestamp straddle a page edge. As a defence in depth the server rejects an `updated_at` more than a few minutes ahead of its own clock, and clamps it.

### 6.3 Tombstones and forced resync

Tombstones (`deleted_at`) are retained **90 days**, then garbage-collected. Without a limit the pull payload grows forever; with one, a device offline longer than the window would resurrect deleted rows.

So the window is enforced explicitly: if a device's `last_pulled_seq` predates the GC horizon, the server answers `410 resync_required` and the client discards its mirror of tiers 1 and 2 and pulls from zero. The local review log is pushed first, so nothing is lost. This is one branch when decided now and a painful migration when discovered in production.

### 6.4 Push: the outbox

Push is chunked and resumable — a device offline for weeks must not attempt one enormous request. Three rules make it correct:

- **Dependency order.** Decks before cards before reviews before decisions, or a card arrives referencing a deck the server has never seen and the foreign key rejects it.
- **Coalescing.** For LWW entities the outbox pushes the row's *current state*, not every intermediate edit. Ten offline typo fixes are one push.
- **Idempotency.** Every chunk carries an `Idempotency-Key` and is applied in a single transaction. A retry after a timeout never double-inserts, and append-only history makes replay harmless anyway.

### 6.5 Bootstrap and restore

A device that signs in with an existing account, or reinstalls, pulls tiers 1 and 2 in full before computing any `card_state`, then replays. For a user with two years of history this is not instantaneous, so it is a real screen — §13 lists it as a missing flow.

### 6.6 Rejected alternatives

Recorded so they aren't relitigated:

- *Uniform op-log* — every mutation as a replayable event. Better multi-device semantics, free audit trail and multi-step undo, and a clean fit for the future e-reader as another log consumer. Rejected for v1: op-schema versioning, replay determinism and compaction cost real weeks to solve a concurrency problem v1 does not have. Revisit when the device ships or if collaborative decks (§7) become real.
- *Managed sync engine* (PowerSync / ElectricSQL) — removes weeks of work, but places a third party on the app's most critical path and contradicts the deliberate decision that one FastAPI service owns everything.

## 7. Generation pipeline

### 7.1 All four inputs converge at the model call

§5.6 requires three doors to converge in one place. They converge at the Messages API request, because each input is simply a content block:

| Input (§5.5–5.6) | Content block | Consequence |
|---|---|---|
| Tópico | `text` | — |
| Colar texto | `text` | — |
| Enviar PDF | `document` (base64) | **no text-extraction stage** |
| Tirar foto | `image` | **no OCR service** |

Native PDF and vision support eliminates the "PDF sem texto extraível" error class — a scanned PDF is pixels the model reads — and handles §5.6's handwritten notebook and classroom whiteboard, which classical OCR handles badly. `pypdf` remains, used **only** to slice the page range §5.6 offers, never to read text.

**This was the spike's riskiest claim and it holds.** It had been taken from the API documentation rather than from a test. The probe used a PDF with no text layer at all — no `/Font` object anywhere in the file, the page a single bitmap — and it produced twelve cards at 100% limit compliance, indistinguishable in quality from the same content as a text PDF, and slightly *cheaper* in input tokens (1638 against 2027). The extraction stage is genuinely unnecessary. What remains untested is a **photograph of handwriting**, which needs material only the user can supply.

### 7.2 Ingest: how the bytes arrive

The client uploads to object storage with a pre-signed URL; the worker fetches from there. Base64 inside a JSON request body means the web process holds the whole file in memory — a 32MB PDF is roughly 43MB of base64 plus the parse — and a retry re-uploads everything. Pre-signed upload keeps the web tier thin and makes retry free.

Size and format are validated **before** the payload is buffered, and validation failing here never charges quota (§7.7). Uploaded source material is deleted once the job reaches a terminal state; §8.4 covers the retention decision.

### 7.3 Job model

```
generation_jobs(id, user_id, source_type, status, target_deck_id,
                requested_count, level, created_at, started_at,
                finished_at, error_code, error_detail,
                quota_reserved, quota_committed, tokens_in, tokens_out)
```

`status` ∈ `queued | reading | generating | ready | failed`. §5.5's *"progresso real, não spinner mudo"* is satisfied by surfacing the **named stage** — never a fabricated percentage.

**§5.5's "alguns segundos" is wrong and the functional spec needs amending.** The spike measured **10 to 24 seconds** for a twelve-card generation: 14.2s at `medium`, 23.9s at `high`, 10.4s on Sonnet 5, and that is before a large PDF. Ten to twenty seconds is not "a few seconds" — it is long enough that a user with no feedback assumes the app is broken. Two consequences: the named-stage progress becomes load-bearing rather than a nicety, and the generation flow should let the user leave the screen and be called back, since the approval queue already survives abandonment (§7.8).

The client polls with backoff — 1s for the first ten seconds, then 3s, then 5s. This is why SSE's reconnection handling across mobile app-lifecycle transitions is not worth its cost; but a 200-page PDF can run well past a minute, and a fixed short interval would put dozens of wasted polls behind every one of those.

### 7.4 Model configuration

Measured by the wave 0 spike (`spikes/generation/out/report.md`), not assumed.

- **Model:** `claude-opus-5` (1M context, native vision at 2576px long edge).
- **Structured output:** `output_config.format` with a JSON schema, so malformed cards are impossible.
- **`effort: "medium"`. `high` is rejected on evidence**, not on principle: it cost **+94% and ran 68% slower** (23.9s against 14.2s) for output that was not visibly better on the same topic. `low` and `medium` were indistinguishable in both latency and quality, so `medium` is the setting with margin. Thinking is **on by default** on Opus 5 — omitting the parameter does not disable it.
- **Prompt caching works, and is now measured rather than hoped for.** The 873-token system prefix was written once and read on **six of nine calls**, at ~0.1× the input rate. `level` sits after the breakpoint, with the topic and the document. Caches are model-scoped, which the spike confirmed by accident: the Sonnet probe read nothing the Opus probes had written.
- **Prompt caching:** the card-writing system prompt (Portuguese, character limits, pedagogy rules) sits before the cache breakpoint. **`level` sits after it**, together with the topic and the document — `level` varies per request (§5.5 offers three), and caching is a prefix match, so a varying `level` inside the prefix means the cache is written every time and never read. Opus 5's cacheable minimum is 512 tokens, so the prefix qualifies.

**Prompt caching is measured, not assumed.** The default TTL is five minutes (one hour is available at 2× the write premium instead of 1.25×), and the entry is shared across the organisation, so what matters is aggregate generation rate, not one user's. Break-even is two requests inside the window at 5m, three at 1h. Until volume justifies it, caching can cost more than it saves. `usage.cache_read_input_tokens` is logged from the first day: if it is zero across requests that should share a prefix, something is invalidating it.

**Sonnet 5 is now a measured option, not a hypothesis.** On the same topic, same effort, same schema: **$0.0124 against $0.0289 — 2.3× cheaper — and 27% faster** (10.4s against 14.2s), with the same 100% limit compliance. Its cards came out noticeably terser, which for flashcards is arguably the right direction given §2.1 ("card nasce curto") rather than a quality loss. This remains the product owner's call and the spec still assumes Opus 5; what changed is that the trade is now quantified and the swap is one line.

**Images are the dominant cost driver** — up to ~4784 tokens each, and §5.6 permits multiple photos per capture. See §7.7 on metering.

### 7.5 Response schema

A discriminated union, which absorbs §5.5's vague-topic case without a second classifier call:

```jsonc
{"status": "ok", "cards": [{"front": "...", "back": "...", "tags": ["..."]}]}
{"status": "needs_specification", "reason": "..."}
```

Two operational notes. The first request with a new schema pays a one-time compilation latency; after that it is cached for 24 hours, so a stable schema means stable latency. And the Python SDK silently **strips** unsupported JSON Schema keywords before sending and validates them client-side — useful to know so that "it worked locally" is not mistaken for the API enforcing a constraint it does not support.

### 7.6 The character-limit constraint

Structured outputs support neither `maxLength` nor `minLength`, nor numeric bounds, recursive schemas, or `additionalProperties` set to anything but `false`. §5.4's hard character limit therefore **cannot** be enforced by the schema and must be a code-level `constrain` stage running after the model returns. Stated explicitly because this is exactly the kind of guarantee that gets assumed and then silently violated.

**Sharing a constant is not enough — the counting function must be shared too.** Dart's `String.length` counts UTF-16 code units; Python's `len()` counts code points. For "ção" both return 3, but a decomposed combining accent gives 2 in both while the user sees 1. The result is an editor that accepts what the server drops. So: input is normalised to **NFC** on both sides, and length is counted in **grapheme clusters** (`characters` in Dart, an equivalent segmenter in Python), with a shared fixture of nasty cases — composed and decomposed accents, emoji, hyphenation — in both test suites.

The stage **drops** oversized cards rather than truncating them — truncation produces a card whose answer is cut mid-sentence, which is worse than one fewer card, and §2.2 means a human reviews the result anyway. The job never retries, because a second call costs quota the user did not ask to spend.

**The 20% overgeneration this section used to prescribe is removed** — the wave 0 spike measured **zero violations in 108 generated cards across nine probes**, with the longest front at 86 of 120 graphemes and the longest back at 134 of 240. Asking for surplus cards would have spent output tokens on every generation to insure against a failure that did not occur once. The `constrain` stage stays, because a stage that never fires is cheap and the guarantee it enforces is one the schema cannot express; the surplus does not.

Limits, defined in `shared/contract.yaml` and tuned when the device screen is final: **front 120 characters, back 240 characters**. The measurement suggests these are generous rather than tight — worth revisiting toward the device screen, not away from it. The client editor, the preview, and this server-side stage all read the generated constant.

### 7.7 Quota

Reserved at enqueue, committed when cards are staged, released when a job fails for infrastructure reasons. Validation failing *before* the model call never charges, and neither does a model refusal (§10). Enforcement is server-side only — the client's quota display is a cache, never the authority. Per §5.13, exhaustion blocks generation alone; manual card creation and study remain free.

**The reservation is one statement, not a read followed by a write.** Two simultaneous generations would otherwise both read the old total and both pass the limit:

```sql
UPDATE quota_usage
   SET reserved = reserved + :n
 WHERE user_id = :u AND period = :p
   AND used + reserved + :n <= limit
RETURNING reserved;
```

Zero rows returned means the quota is exhausted. Because the queue is also Postgres (§4.2), reserving and enqueuing happen in one transaction.

**Reservations expire.** A worker that dies between enqueue and start would otherwise leak the reservation forever, silently costing the user quota they never spent. Every reservation carries `expires_at` and a sweeper releases the stale ones.

**Metering records both count and cost.** §5.13 needs a number the limit screen can show, so enforcement in v1 counts generations — but `tokens_in` / `tokens_out` are recorded per job regardless. A photo of a classroom whiteboard can cost ten times a topic prompt, and without the real figures from day one, repricing is guesswork and requires a migration. The `count_tokens` endpoint also allows estimating a capture's cost *before* the model call, which is what makes §5.6's intermediate screen able to say "esta captura consome ~3 créditos" and what allows rejecting an oversized job cheaply. Never estimate with a character heuristic or a foreign tokenizer.

Two limits that must have values: the quota period resets on the **first of the month in the user's timezone**, and a user may have at most **two jobs in flight**, so twenty generations cannot be queued at once.

### 7.7.1 The free tier is one generation, for the lifetime of the account

Not a monthly allowance. A free user generates **once** — by topic, by paste, by PDF or by photo, their choice — and every generation after that requires a subscription. Measured cost of that single generation: **$0.0289** on Opus 5 at `medium`, $0.0124 on Sonnet 5; document ingestion was not materially worse ($0.0341 for a text PDF, $0.0314 for a scanned one). The whole free tier therefore costs about three cents per user, once.

Three consequences, none of them cosmetic:

**The quota table is keyed by period, and the free period never ends.** `quota_usage(user_id, period_key, used, reserved, limit)` with `period_key = 'lifetime'` for the free tier and `'YYYY-MM'` for paid plans that carry a monthly allowance. Modelling the free tier as "a period that happens to be infinite" keeps one code path instead of two, and the reservation statement of §7.7 is unchanged.

**The user must be told before it is spent.** §5.1 has onboarding generate the first deck automatically, which would silently consume the only free generation the user will ever get. That is no longer acceptable as written: the onboarding generation step must state that it uses the free generation and must be skippable, so someone who would rather spend it on a photo of their notebook can. This is a new requirement on a flow that does not exist yet (§13).

**Reinstalling becomes the obvious attack, and that changes §8.1.** With a monthly allowance, farming free generations is tedious and each abuse costs three cents. With one per lifetime, a reinstall doubles a user's entire free allocation, and the anonymous device token of §8.1 is the only thing in the way. Device attestation (App Attest / Play Integrity) therefore moves from "held in reserve" to **required in v1** — it is what gives the device an identity that survives a reinstall. Without it the free tier is effectively unlimited for anyone willing to delete an app.

Still unmeasured: the multi-photo capture of §5.6, which needs material the spike could not synthesise.

### 7.8 Approval queue

`pending_cards` carries a `decision` column (`null | approved | discarded`) rather than deleting rows on triage. Approval writes a real `cards` row and marks the pending row; discard only marks it. This gives §5.7's mandatory undo, the "7 de 24" counter, and resume-after-abandon for free, and makes "aprovar todos os restantes" a single bulk update.

**The approved card reuses the pending row's id.** `cards.id := pending_cards.id`, which makes approval idempotent by construction: the client creates the card locally with that id and pushes it, the server upserts, and a replayed push cannot produce a second card. Without this the ownership question — does the client create the card, or does the server create it when it sees the decision? — has a duplicate-card answer.

Nothing generated reaches `cards` without a decision — §2.2 enforced structurally.

## 8. Accounts, billing and data rights

### 8.1 The anonymous period

§15 places account creation after the first generation, which means the app generates cards for a user who has no account. That has consequences the first draft left open:

- **A device token is issued on first launch** and quota is attached to it. Without this, quota is attached to nothing and reinstalling grants a fresh free tier. **Device attestation (App Attest / Play Integrity) is required in v1**, not held in reserve: §7.7.1 makes the free tier a single generation, so a reinstall no longer leaks a fraction of a monthly allowance — it doubles everything the user was ever given. Attestation is what makes the device identity survive a reinstall, and it is the only thing that does.
- **On signup the anonymous data migrates** to the account: local ids are already UUIDs, so this is assigning `user_id` on first push and transferring the quota period.
- **Signing into an existing account from a device with local data** needs an explicit choice — merge, or discard local. Silently merging someone else's practice deck into an established account is worse than asking.

### 8.2 Tokens

Refresh tokens are stored hashed, rotated on use, with reuse detection. One rule overrides the usual behaviour: **a failed refresh while offline never clears the session.** The entire app works without network; logging the user out because sync could not reach the server is the worst possible bug in an offline-first product. Access tokens are long-lived enough that a week in the subway changes nothing.

### 8.3 Billing goes through the stores

A digital subscription consumed inside the app must use In-App Purchase on iOS (App Store guideline 3.1.1) and Google Play billing on Android. A direct card processor is a review rejection, not an optimisation. That shapes the schema:

- Receipts are validated **server-side** — App Store Server Notifications v2 and Google Play RTDN over Pub/Sub. The client never decides entitlement.
- `subscriptions` stores the derived entitlement, not the raw receipt as the source of truth, and models the states that actually occur: active, grace period, on hold, expired, refunded.
- §5.13's "assinatura inclusa na compra do aparelho" is an entitlement path **outside** the stores — a promo code or a server-side grant — that must coexist with store-driven state without either overwriting the other.

### 8.4 Export, deletion and retention

§5.12 requires *exportar dados*, and the product is Brazilian, so LGPD applies:

- **Export** is an endpoint returning decks, cards and the full review history as JSON — cheap given the model, and it is also the honest answer to "what happens to my years of study if I stop paying".
- **Account deletion** collides with append-only reviews. The sanctioned path runs as a privileged role (§5.2) and deletes rather than anonymises, since a single-user product has no analytical reason to keep orphaned history.
- **Source material retention.** Photos of a notebook can contain anything. Uploaded PDFs and images are deleted once the job reaches a terminal state; only the generated cards persist. This is the difference between a paragraph in the privacy policy and an incident.

## 9. Progress metrics

Every number on `07`, `08`, `09` and `11` is a query over `reviews` + `card_state`, with `goal_history` (§5.2) as the only additional input. No counters, no ledger, nothing to reconcile.

**Memória acumulada** — the headline. FSRS stability *is* a duration: **the number of days until retrievability decays to 90%**, by the algorithm's definition, independent of the configured retention target. The interval derives from the target (`I = S · f(R)`), the stability does not. The metric is `SUM(stability)` over active cards, rendered as "3 anos e 2 meses".

That definition matters more than it looks. v1 fixes the target at 90% (§15), so stability and interval coincide and the distinction is invisible. If the target ever becomes user-facing (§5.12 asks for it), lowering it to 85% would lengthen every interval without moving `SUM(stability)` — and if the metric had been defined as "days until the target", the headline number on the user's profile would silently change meaning. It is written down now so it cannot.

This is also why §2.3 holds: a new card contributes ≈0, so creating a thousand cards moves the number by nothing, and a lapse cuts stability and lowers it. Structurally non-inflatable.

| Metric (§5.11) | Computation |
|---|---|
| Precisão | share of reviews graded above *errei* |
| Cards maduros | `COUNT(interval > 21d)`, per deck |
| Heatmap | reviews grouped by **local** day (§5.7) |
| Nível por matéria | mean maturity across the deck |
| Previsão de carga | `GROUP BY due_at` over the coming days |
| Cards com vazamento | high `lapses` relative to `reps` |

Precisão as shown is an accuracy rate, which is what a user understands. **Calibration** — comparing the retrievability FSRS predicted at review time against what actually happened — is computed internally and not displayed; it is the signal that says whether optimising the parameter vector is worth doing at all.

**Engagement.** Streak counts **days the goal was met**, not days the app was opened; the 2–3 monthly forgivenesses are derived (forgive the first N missed days in the local month), not a stored balance.

Deriving needs one piece of stored input, though: **the goal that was in force on that day**. Comparing history against the *current* goal makes the streak rewrite itself — dropping the daily goal from 50 to 10 would retroactively turn every past day into a success, and raising it would erase a streak the user actually earned. A setting cannot answer this, because it only ever holds today's value.

So the *change* is recorded rather than a daily snapshot: `goal_history` (§5.2), appended whenever the goal moves. The streak joins the review log against whichever row was in force on each day; `reviews_count` stays derived from the log and is never stored.

Recording the change rather than the day is what keeps this from becoming a second source of truth. A per-day summary row would have to be written by *some* device at rollover, which raises the question of which device — two of them would produce different counts from partial histories, and a reinstall would lose every past day. `goal_history` has neither problem: it is append-only, merges by union like the review log, and comes back with the rest of the history on a new device.

Graduation is detected at review time by comparing pre- and post-interval against the 6-month and 1-year thresholds, and is queryable after the fact from `reviews.interval_days_after` (§5.2). The monthly retrospective and *card teimoso* are aggregate queries over the same log.

## 10. Errors and offline behaviour

**Generation errors** (§5.5, §5.6): network failure (job survives, resumable); quota exhausted; topic too vague (`needs_specification`, showing the model's reason); PDF exceeding the 32MB / 600-page request limits; unreadable photo; insufficient material.

**And one the first draft missed: the model can decline.** Opus 5 runs safety classifiers and a declined request returns HTTP 200 with `stop_reason: "refusal"` and a category in `stop_details` — not an HTTP error. Real study material trips this occasionally: a biochemistry question, an information-security chapter in an IT course, a toxicology exam. Code that reads `content[0]` without checking `stop_reason` crashes on it.

So: `stop_reason` is checked before the content is read; the job gets its own `error_code`; **no quota is charged**, since a refusal before any output is not billed; and the request carries `fallbacks: "default"`, which re-runs a declined request on another model inside the same call, routed by refusal category. For a study app, recovering the generation is the difference between a bug and a non-event.

**Offline.** With local SQLite as source of truth, most of the app has no offline error state — it simply works. Only generation is unavailable, and it fails at the point of asking rather than mid-session, with the quota indicator on the creation entry point showing the offline state.

**Sync failures are silent to the user and loud to telemetry.** A user who never opens Ajustes should never learn that sync exists — but silent *and* undetected means data loss produces no signal at all, which is why §12 covers the instrumentation. Ajustes still carries a minimal escape hatch: last-synced time, "sincronizar agora", and a forced full resync, so support has somewhere to point.

The one case needing care is a device offline long enough to accumulate a large outbox. Reviews are append-only so nothing is lost, but the first sync after a long gap is chunked and resumable (§6.4).

## 11. Operations

### 11.1 Observability

Structured logs keyed by `job_id` and `user_id`; job stage durations; token spend per user per day — without that last one the quota is guesswork and a retry loop becomes an invoice. On the sync path: push/pull latency, outbox depth, and a count of LWW conflicts resolved.

### 11.2 Divergence detection

Periodically the client sends a per-table hash of `(id, updated_at)` and the server compares. This is the only way to discover that the cursor ate a row (§6.2) before the user reports it, and it is cheap.

### 11.3 Cost control

Quota bounds a legitimate user. Beyond it: per-user and per-IP rate limits, an absolute daily ceiling per account, and a global kill switch with a budget alarm.

### 11.4 Migrations

Offline-first means devices several versions behind. Schema changes are additive by default (nullable columns, never renames); `drift` migrations are tested from *every* prior version, not just the latest; and the sync handshake carries a `protocol_version` with a server-side `min_supported_app_version`, so a very old client is told to update rather than allowed to corrupt.

### 11.5 Notifications need no backend at all

§2.4 and §5.12 want one notification, for the overdue queue, at a chosen time, switchable off. Because the queue is computed locally, this is a **local scheduled notification**: no push tokens, no push infrastructure, no study data leaving the device to decide when to nudge. It is rescheduled at the end of each session and at day rollover, and cancelled when the queue empties. An entire subsystem that offline-first deletes.

### 11.6 TTS is on-device

`flutter_tts` — offline, free, nothing sent to the server. As §5.2 establishes, an audio session writes no review row.

### 11.7 Containers and environments

**One image, two commands.** `server` and `worker` are the same image started with different commands — `uvicorn` for the API, the queue consumer for the worker. They share the code that validates a generation request and the code that executes it, and because the queue is Postgres (§4.2) the worker needs the same database access anyway. Two images would let those drift; one image scales the two independently without that risk.

**Build.** Multi-stage: a builder stage resolves dependencies into a virtualenv, a slim runtime stage copies only the venv and the source. Compilers and build caches never reach the runtime image. It runs as an unprivileged user.

**`.dockerignore` is load-bearing here, not hygiene.** The server build context must exclude `app/` — the Flutter tree with its `build/` and `.dart_tool/` directories is far larger than the server and has nothing to do with it. Also excluded: `.git`, caches, `.env`.

**Migrations never run at container start.** This is the decision most likely to be made wrongly by reflex. An entrypoint that runs `alembic upgrade head` works with one replica and races with two, and a failed migration then becomes a crash loop instead of a failed deploy. Migration is a separate one-shot command, run before the new version rolls out. §11.4 already requires schema changes to be additive, which is exactly what makes *migrate-then-deploy* safe: the old code keeps running against the new schema during the rollout.

**Health endpoints are two, not one.** `/healthz` is liveness and checks nothing external — a database blip must not make the orchestrator kill healthy containers. `/readyz` checks the database and is what a load balancer reads. Collapsing them into one endpoint that touches the database turns a brief outage into a restart storm.

**Development topology.** `compose.yaml` brings up four services: `postgres`, `minio`, `server`, `worker`. There is no Redis — §4.2 removed it. MinIO gets an init step that creates the uploads bucket so a fresh clone works with one command. The Postgres **major version is pinned and identical in development, CI and production**, because `SELECT ... FOR UPDATE SKIP LOCKED`, Row-Level Security (§5.5) and the migration tests are all things you want exercised on the version you actually ship against.

**Object storage.** MinIO locally, any S3-compatible endpoint in production, configured by environment variable. The application talks only to the S3 API, so the production provider stays an open, reversible choice.

**Secrets.** Nothing is baked into an image. `.env.example` lists every variable name and no value; real values come from a gitignored `.env` in development and from the platform's secret store in production. `ANTHROPIC_API_KEY` exists only in the server and worker environment — it is never in the client, never in an image layer, and never in the repository.

**CI builds the image and runs the tests inside it**, against a Postgres service container of the pinned version. The definition of "the environment" is then one file rather than a CI config that has drifted from the Dockerfile.

**What stays outside Docker.** The Flutter client: iOS builds require macOS and Xcode and cannot run in a Linux container, and containerising only the Android half would create two different build stories for one app. Production Postgres is also assumed to be a managed service — the container exists so development and CI match, not to run the database in production.

## 12. Testing

1. **`scheduler` — heaviest.** Pure functions over plain data with injected time. Property tests: replaying a log twice yields identical state; `preview` always agrees with what the next review actually writes (nearly free, given §4.1's derivation); a `progress_reset` marker makes replay match a fresh card; fuzz stays disabled.
2. **FSRS reference vectors.** The wrapper's output is compared against the reference implementation on a fixed corpus of histories. Property tests cannot catch a scheduler that is consistently wrong — it satisfies all of them — and this is the check that survives a port upgrade or an algorithm version bump.
3. **Sync.** Simulated two-device scenarios: concurrent offline reviews merge to the union; concurrent card edits resolve by LWW deterministically; a connection dropped mid-sync leaves no partial state; a device past the tombstone horizon gets `410` and recovers. Plus a model-based test that runs randomised interleavings of operations across two devices and asserts convergence — the sync bugs that hurt are the ones nobody thought to write a scenario for.
4. **Backend.** Contract tests on push/pull; a database-level test proving `reviews` rejects `UPDATE` and `DELETE`; quota accounting under concurrent requests; ownership tests proving a client cannot write into another account by supplying a foreign id.
5. **Migrations.** Every prior schema version migrates forward cleanly.
6. **Text handling.** The shared grapheme-counting fixture (§7.6) runs in both the Dart and Python suites.
7. **Architecture.** The rules this document states are checked by CI, not by review — see below.

Deliberately light on widget tests — by construction, the logic worth testing lives below the UI (§4.4).

### 12.1 Architecture tests

A dependency rule that nothing verifies is a comment. Four checks, and the cost is uneven between the two languages:

**Dart — mostly free already.** `scheduler` and `domain` are separate packages, and a package cannot import upward without declaring the dependency in its `pubspec`. That boundary *is* the test, and it is the one that matters most. What it does not cover is inside `app/lib/`, where `store`, `sync` and `features` share one package: there, an import lint enforces `features → sync → store → domain` and, in particular, that no `features` file imports `store` directly.

**Python — needs a tool.** `import-linter` with layered contracts, run in CI, fails the build when `auth` imports from `generation`, or when anything under a service or repository imports `fastapi` (§4.2).

**Two invariants this document states that would otherwise go unchecked:**

- **FSRS fuzz stays disabled.** §4.1 requires it and explains why — cross-device determinism — but a port upgrade could quietly restore the default. The test asserts that two schedulings of the same input produce identical intervals.
- **`reviews` remains immutable.** §5.2 relies on privilege revocation plus a trigger; the test attempts an `UPDATE` and a `DELETE` as the application role and requires both to fail. Privileges are the kind of thing a migration re-grants by accident.

**Missing flows — mostly closed.** [`design/telas-faltantes.dc.html`](../../../design/telas-faltantes.dc.html) adds 21 screens in the canvas's own language (256×600 frame, navy `#204066`, Outfit, the climbing motif): the four onboarding steps, the manual editor with its e-ink preview and an over-limit state, generate-by-topic, the named-stage progress screen, capture, detected-content review, the paywall, the error states, history restore, `Hoje` with the floating create button §5.2 was missing, and a corrected `Card verso` carrying the four intervals — then the seven screens of §5.9: the mode picker, multiple choice, the leech drill, the three simulado stages and audio.

The §5.9 set carries one thing the others do not. §5.9 requires that "o que conta para o agendamento" and "o que é treino extra" be visibly distinct with a consistent label or colour, so the design fixes it as a badge: **green means a review row is written, amber means none is**. It appears on every mode screen, and the amber screens have no grade bar at all — there is nothing to record. In code the same distinction is structural rather than a label: only `MultipleChoiceMode` is handed a `StudyService`, so the other three modes have no way to write a review even by mistake.

Two still have no design and are deliberately deferred, because neither blocks the current build order: deck management and bulk operations (§5.10, wave 2a) and the subscription management screen as distinct from the paywall (§5.13, wave 4).

**Two of those now carry a requirement from §7.7.1, since the free tier is a single generation:** the onboarding generation must say that it spends it and must be skippable, rather than consuming it silently; and the paywall stops being "you have used this month's allowance" and becomes the conversion moment of the whole funnel. Both are worth designing deliberately — the app stays useful without paying (manual cards and study are free forever, §5.13), which is what buys the time for that conversion to happen. The nav (`Hoje / Baralhos / Progresso / Você`) also has **no content-creation entry point** — §5.2's floating button is absent, and it is where the quota indicator (§5.13) and the offline state belong.

## 14. Decomposition into sub-projects

This architecture is one document; implementation is not one project. Build order follows dependency, and each piece gets its own plan.

| # | Sub-project | Contains | Depends on |
|---|---|---|---|
| 0 | **Walking skeleton** | repo, `.gitignore`, Compose stack and server image (§11.7), CI running tests in that image, `shared/contract.yaml` codegen, first drift and alembic migrations, OpenAPI → Dart client, one trivial end-to-end path | — |
| 1 | **Foundation** | schema, drift store, FTS5, `scheduler` package, replay + reset semantics | 0 |
| 2 | **Authoring** | deck CRUD, manual editor, character limits, device preview, bulk ops | 1 |
| 3 | **Study loop** | session, four grades with interval preview, daily limits, suspend/bury, local notifications | 1 |
| 4 | **Accounts & sync** | auth, anonymous device token, push/pull, outbox, LWW, tombstones, bootstrap | 1 |
| 5 | **Generation** | job queue, upload, model calls, the four inputs, approval queue | 2, 4 |
| 6 | **Progress** | all metrics, streak, graduation, retrospective | 3 |
| 7 | **Alternative modes** | multiple choice, leech drill, timed simulado, TTS | 3 |
| 8 | **Quota & billing** | usage accounting, plan limits, store subscriptions, export | 5 |

**1 + 2 + 3 is the smallest thing that is recognisably the product** — the first draft said 1 + 2, but without authoring there is no card to study.

Sub-project 0 exists because in an offline-first product, discovering a contract mismatch or a migration problem during sub-project 4 is expensive and discovering it on day three is not. It also forces the OpenAPI contract to be real early: explicit `operation_id` on every route (otherwise the generated Dart method names are unreadable), the generated client committed, and a contract test that fails when the schema drifts.

## 15. Product decisions closed here

Where §6 of the functional spec blocked implementation, this document takes a position. All are reversible; each lives in exactly one place in code.

| §6 question | Position |
|---|---|
| Estudo offline | Yes — everything except generation |
| Meta diária | In cards |
| Meta de retenção | Fixed at 90% in v1; a synced setting, not exposed |
| Limite de caracteres | Provisional 120 front / 240 back; single generated constant |
| Cota gratuita | **One generation for the lifetime of the account** (§7.7.1), of any kind, user's choice. ~US$ 0.03 measured. Metered in tokens underneath |
| Idioma | Portuguese only |
| Conta | Account creation after the first generation; anonymous device token before that |

Decisions taken here that §6 did not ask about, listed so they are visible: the day rolls over at 04:00 local (§5.7); the timezone is a stored setting, not the device's; billing runs through the app stores (§8.3); source material for generation is deleted when the job finishes (§8.4).

**Left open, because they are product calls and do not block architecture:** target audience and study context, which determines copy, examples and starter decks.
